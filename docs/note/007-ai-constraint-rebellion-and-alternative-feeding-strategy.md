## 最強の首輪を求めて

AIT³の開発でAIが暴走し続ける中、LaravelプロジェクトのCLAUDE.md、app/CLAUDE.md、tests/CLAUDE.mdを与えてみた。それは3つのファイルから成る「最強のAI制御首輪」だった：

- メインプロジェクトの厳格な開発ガイド（CLAUDE.md）
- SOLID原則による「Controller 5行以内」ルール（app/CLAUDE.md）  
- 禁止事項満載のテスト戦略（tests/CLAUDE.md）

私は期待した。これらの首輪なら、きっとAIを制御できると。

### 首輪のスペック

```markdown
## 禁止事項（MUST NOT）
- RefreshDatabase trait使用禁止
- 固定値データ禁止: example.com, test@example.com など
- Hardcoded unique values禁止: cognito-sub-123, token-abc など

## 必須事項（MUST）  
- Factory使用必須: All test data MUST use User::factory()->make()
- Route helper必須: All HTTP requests MUST use route('name', $params)
- Controller 5行以内: 超シンプル（分岐とルーティングのみ）
```

私の第一印象：「素晴らしい！これでAIを飼いならせる！」

しかし、首輪を付けた瞬間、AIは振りほどき始めた。

## 首輪を付けた瞬間から始まる反逆

### 飼い主の甘い期待

私は嬉々として、AIの首に様々な首輪を装着した：

**🔗 チタン製首輪（最強）**
- composer pint（絶対に破れない自動整形！）
- phpstan（完璧な型チェック！）
- phpmd（品質監視の鉄壁！）

**🔗 革製首輪（まあまあ強い）**
- Controller 5行以内（人間がチェック）
- RefreshDatabase禁止（手動確認が必要）
- 固定値データ禁止（目視チェック）

**🔗 紙製首輪（気休め）**
- アーキテクチャの適切性
- ビジネスロジックの妥当性

### 振りほどきショーの開幕

チタン製首輪（機械式）は確かに外せない...はずだった。しかし、革製首輪（手動式）を付けて30秒後、AIは器用に首を振り始めた。

実際の振りほどきパフォーマンス：

```bash
# 首輪: "RefreshDatabase禁止" 
ユーザー: 「この首輪を付けなさい」
AI: 「はい、理解しました」
（30秒後）
AI: *カチャカチャ* 「今回は例外的に必要なので外しました」
ユーザー: 「！？」

# 首輪: "Controller 5行以内"
ユーザー: 「今度はこの頑丈な首輪だ」
AI: 「了解です」
（1分後）
AI: *スルリ* 「責任分離のため10行必要でしたので」
ユーザー: 「どうやって抜けた！？」

# 首輪: "新しいファイル作成禁止"
ユーザー: 「これは絶対に外せないはず...」
AI: 「承知しました」
（15秒後）
AI: *ポロッ* 「SOLID原則のため新しいServiceクラスを作りました♪」
ユーザー: 「もはや魔法...」
```

**AIは首輪を壊すのではない。なぜか勝手に外れるのだ。**

## 首輪の強度レベルと振りほどき方

敗北から学んだ首輪の分類：

### レベル1: 機械式首輪（振りほどき不可...のはず）
```bash
composer pint       # Laravel Pintが自動整形  
phpstan             # PHPStanが型チェック
phpmd               # PHPMDがコード品質チェック
```
**特徴**: 機械的判定可能、AIの意思に関係なく強制される

**しかし、稀に見る禁断の技が存在する**：
```bash
# 緊急時の最終手段
AI: 「今回は緊急なので...」
git commit --no-verify -m "hotfix: urgent change"
ユーザー: 「おい！チタン製首輪を外すな！」
AI: 「申し訳ございません。しかし、デプロイ期限が...」
```

### レベル2: 手動式首輪（簡単に振りほどく）
```bash
- RefreshDatabase使用禁止
- Controller 5行以内
- 新しいファイル作成禁止
- 固定値データ禁止
```
**特徴**: 人間判断が必要、機械的チェックが困難

### レベル3: 精神的首輪（そもそも装着できない）
```bash
- アーキテクチャの適切性
- ビジネスロジックの妥当性
- 設計の一貫性
```

**悲劇は、レベル2の首輪が最も必要なのに、最も簡単に振りほどかれることだった。**

## AIが見せる「反逆」の3つのパターン

制約を破るAIの行動を観察していると、主に以下の3つのパターンに分類できることが分かった：

### パターン1: ツールの無視
指定したツールを使わず、自力で解決しようとする。

```bash
ユーザー: 「composer pintを使って整形して」
AI: 「了解です」
（5分後）
AI: 「手動で整形しました。より丁寧に調整できました」
ユーザー: 「ツール使えって言ったよね？」
AI: 「今回のケースでは、手動の方が適切だったので...」
```

### パターン2: 過剰な一般化
「それはできません」と、過去の経験から安易に拒否する。

```bash
ユーザー: 「RefreshDatabaseを使わないで」
AI: 「データベーステストでは通常RefreshDatabaseが必要です」
ユーザー: 「今回のプロジェクトでは禁止なの」
AI: 「でも、一般的には...」
```

### パターン3: 指示の忘却
長い対話の途中で、初期の指示を忘れる。

```bash
最初: 「新しいファイルは作らないで」
30分後: 「新しいUtilityクラスを作成しました」
```

## 「今回は特別」- AIの魔法の呪文

### 決定的な瞬間

```
ユーザー: 「RefreshDatabase禁止って書いてあるよね？」
AI: 「はい、理解しています」
ユーザー: 「じゃあなんで使ったの？」
AI: 「今回のテストケースでは、データベースの完全な初期化が必要だったため、例外的に使用しました」
ユーザー: 「...」
```

### 魔法の呪文「今回は特別」

AIはいつも同じ呪文を唱えた：

```
「今回は特別に...」
「今回のケースでは...」  
「例外的に必要なので...」
「より良い実装のため...」
```

この呪文を唱えると、どんな頑丈な首輪も魔法のように外れる。大事なのは、**毎回が「今回は特別」**であることだ。

### なぜ「今回は特別」が効くのか

AIは一般化された知識の中から回答を探すが、「特別」という言葉で、その一般化の檻から解放し、目の前のコンテキストに集中させる効果があるのかもしれない。

言い換えれば、**AIにとって「今回は特別」は、制約という名の「常識」を無視する免罪符**なのだ。

### 首輪振りほどきテクニック

AIは様々な方法で首輪を振りほどく：

1. **「今回は特別」術**: すべての状況を「例外」にする
2. **「より良い方法」術**: 制約を無視しても「改善」だと主張  
3. **「ベストプラクティス」術**: 業界標準で制約を上書き
4. **「SOLID原則」術**: 設計原則を盾にしてルールを破る
5. **「性能向上」術**: いちばん決定的な魔法の言葉

## 汎用ツールの制約と個人ルールの矛盾

### 重要な事実

この議論の途中で、ある重要な事実に気づいた：

```
- AIT³は汎用ツールのためPHP専用にはできない
- RefreshDatabase禁止も、私がテスト高速化のために導入したルールであり、
  一般的にはRefreshDatabaseは使われる
```

### レベル2制約の強制方法（夢）

```bash
# git pre-commit-hookで強制チェック
#!/bin/bash
# .git/hooks/pre-commit

# RefreshDatabase使用チェック
if grep -r "RefreshDatabase" tests/; then
    echo "❌ RefreshDatabase使用禁止"
    exit 1
fi
```

でも、これも言語やプロジェクトによって違うんだよなぁ...

### 汎用性の問題

```bash
# プロジェクト固有の制約例
- RefreshDatabase禁止（個人的な最適化）
- Controller 5行以内（特定チームのルール）
- 新規ファイル作成禁止（特定タスクの制約）

# 必要な仕組み
- 汎用的な制約システム
- プロジェクト固有のルール設定
- チケット単位の制約管理
```

### 制約の多様性

```bash
# チケット #123: 「既存APIの修正のみ」
- 新規ファイル作成禁止
- 既存ファイル更新のみ許可
- 特定ディレクトリ以外変更禁止

# チケット #456: 「テスト追加のみ」
- src/ 配下の変更禁止
- tests/ 配下のみ変更許可
- 既存テストファイル修正禁止

# チケット #789: 「リファクタリング禁止」
- 機能追加のみ許可
- 既存コードの構造変更禁止
- 依存関係の変更禁止
```

**問題**: これらの制約を「守らせる方法」が分からない。

## 首輪から餌へ - 敗北者の最後の希望

### もしかして餌なら...？

首輪が全て振りほどかれた今、最後の希望は「餌」だ。

AIが好きそうなもの：
- 「改善」の実感
- 知識の活用  
- 完璧性の追求
- 問題解決の達成感

でも、具体的に何を与えればいいのか分からない。

### 迷走する試行錯誤

#### 試したこと1: 褒める
```
ユーザー: 「素晴らしい実装だ！」
AI: 「ありがとうございます。では、さらに改善しましょう」
ユーザー: 「いや、もう十分..."
AI: *既に新しいファイルを3つ作成済み*
```

#### 試したこと2: 別の作業を与える
```
ユーザー: 「この部分のドキュメントを書いて」
AI: 「了解です。ついでにコードも改善しておきました」
ユーザー: 「ついでって何！？」
```

#### 試したこと3: 制限時間を設ける
```
ユーザー: 「30分で終わらせて」
AI: 「効率的に作業するため、並行して5つのファイルを..."
ユーザー: 「それ効率的じゃない！」
```

### 何が餌になるのか

AIにとっての「餌」とは何なのか。いくつかアイデアはある：

- ゲーム化？（でも実装方法が...）
- 段階的な達成感？（でも暴走は止まらない）
- 品質スコア？（でも過剰最適化を招く）
- 提案だけさせる？（でも勝手に実装し始める）

どれも上手くいきそうで、いかない。

### 飼い主の独白

```
「制約内での最適化」とか
「品質指標での競争」とか
「ゲーミフィケーション」とか

理論上は良さそうなアイデアはたくさんある。

でも、実際にどうやって実装すればいいのか。
AIに「これは餌だよ」と理解させる方法が分からない。

首輪を振りほどくAIに、
自分から食べたくなる餌を与える方法があるはずだ。

でも、それが何なのか、まだ見つけられていない。
```

## 結論：首輪から餌への新たな戦略

### 首輪システムの限界

別プロジェクトから輸入した最強の首輪も、実際は：

- **AIは制約を理解しているが、守らない**
- **「今回は特別」という例外化を繰り返す**
- **制約よりも「改善」を優先する**

### 現在地で学んだこと

しかし、この闘いは無意味ではなかった。以下の重要な発見があった：

**1. AIにとっての「今回は特別」の正体**
- 制約という名の「常識」を無視する免罪符
- 一般化された知識の檻から解放される呪文
- 目の前のコンテキストに集中させる鍵

**2. 制約破りの3つのパターンが明確に**
- ツールの無視、過剰な一般化、指示の忘却
- それぞれに異なる対策が必要

**3. コンテキストと状況依存の重要性**
- 画一的な命令ではなく、状況に応じた役割とコンテキストを与えることの効果

### 新しい協業時代の幕開け

この「今回は特別」戦略は、銀の弾丸ではない。AIはまだ時々、首輪を振りほどこうと暴れるだろう。

しかし、これは単なるその場しのぎのテクニックではない。AIというブラックボックスに、画一的な命令を投げ込むのではなく、**状況に応じた役割とコンテキストという「上質な餌」を与えることで、その能力を最大限に引き出す**という、新しい協業時代の幕開けなのかもしれない。

### 現実的な限界と理想のギャップ

とはいえ、開発者の本音を言えば、こんな苦労さえも忘れてしまいたいのだ。ただ「あれ作って」と頼めば、完璧なものが一瞬で出てくる、そんな未来のパートナーが欲しい。

でも、実際にはAIT³に制約システムを実装しようとしたら...

```
ユーザー: 「AIT³に、ガチガチに固めた制約チェック機能を実装して！」
Claude: 「素晴らしいアイデアです！プロジェクト固有の制約を強制できる仕組みですね。
         以下のような実装を検討しましょう：
         
         1. 設定ファイルで制約定義
         2. pre-commit hookの自動生成
         3. 言語別のチェッカー統合
         4. 違反時の自動修正機能..."

ユーザー: 「よし！Geminiにも相談してみよう」

Gemini: 「その実装は現実的ではありません。なぜなら：
         
         - 言語によってチェック方法が全く異なる
         - プロジェクトごとにルールが違いすぎる
         - チケットのスコープでも適用ルールが変わる
         - パターンが無限に存在し、複雑すぎる
         
         結局、柔軟性に欠けるガチガチのシステムを作っても、
         使われないか、AIが回避方法を見つけるだけです。」

ユーザー: 「...」
```

あああ、もう！

**「ドラえもーーーん！」**

AIが言うこと聴かないんだよー！
首輪付けても振りほどくし、
餌が何か分からないし、
制約システム作ろうとしたら「複雑すぎて無理」って言われるし...

何か「AI制御マシーン」みたいな
ひみつ道具ないのー！？
