# AIT³ Workflow Evolution: Proposed Updates and Critical Analysis

**Date**: 2025-07-17  
**Context**: Refining AIT³ workflow based on AI behavior patterns and practical experience  
**Previous Reference**: 2025-07-08-workflow.md

## 📋 Proposed Workflow Updates (Human Perspective)

### 1. **Enhanced PLAN Phase**

**Current State**: Basic requirements and acceptance criteria  
**Proposed Enhancement**: More detailed upfront planning
- **概要 (Overview)**: High-level description
- **要件 (Requirements)**: Multiple requirements (future: split into child tickets)
- **受け入れ基準 (Acceptance Criteria)**: Clear success metrics
- **設計 (Design)**: Technical approach and architecture
- **テストケース (Test Cases)**: Predefined test scenarios

**Rationale**: More detailed planning helps AI stay on track and reduces drift

### 2. **Constrained RED Phase (Test Creation)**

**Problem**: AI tends to create overly complex or entirely new test patterns  
**Proposed Constraints**:
- Prioritize reusing existing test patterns
- Focus on simple happy paths for each route
- Question whether all edge cases need coverage
- Balance between thorough testing and complexity

**Key Question**: How to instruct AI to write comprehensive yet simple tests?

### 3. **Controlled GREEN Phase (Implementation)**

**Proposal**: Pre-determine files during PLAN phase
- Define which files can be created/modified upfront
- GREEN phase validates adherence to plan
- Enforce SOLID, KISS, DRY, YAGNI through plan compliance

**Goal**: Prevent file proliferation and over-engineering

### 4. **Enhanced REFACTOR Phase**

**Current**: Basic lint, type-check, test  
**Proposed Addition**: 
- Gemini review for dialectical critique
- Verify compliance with original plan
- Human final judgment on acceptance

**Philosophy**: Human intervention at beginning and end

### 5. **New DOCUMENT Phase**

**Problem**: Documentation becomes scattered and outdated  
**Proposed Solution**:
- Dedicated documentation phase
- Clear naming conventions (date, ticket number)
- Chronological organization
- Address AI's tendency to create new files

## 🗡️ Critical Analysis (Claude's Rebuttal)

### 1. **On Detailed Planning**

**Fundamental Issues**:
- **Big Design Up Front (BDUF) Anti-pattern**: Attempting to predict all details before implementation
- **Loss of Emergent Design**: Best solutions often emerge during implementation
- **Rigidity Problem**: Detailed plans become constraints rather than guides

**Counter-proposal**: Keep planning lightweight
- Overview → Requirements → Acceptance Criteria is sufficient
- Let design and test cases emerge naturally in their respective phases
- Preserve TDD's core value: tests drive design, not vice versa

### 2. **On Test Constraints**

**Problems with Proposed Constraints**:
- "Reuse existing patterns" risks copy-paste proliferation
- "Simple happy paths only" creates bug-prone software
- Skipping edge cases invites production failures

**Real Issue**: Not test quantity but test quality
- Solution isn't constraints but better test examples
- Teach good patterns, don't restrict creativity

### 3. **On Pre-determined Files**

**Major Contradiction**:
- YAGNI principle conflicts with pre-planning all files
- Blocks better solutions discovered during implementation
- Forces adherence to potentially suboptimal initial design

**Alternative**: Set boundaries, not blueprints
- Limit number of new files (e.g., max 3)
- Require justification for new file creation
- Allow organic evolution within constraints

### 4. **On Refactor Phase**

**Good Aspects**:
- Dialectical process through Gemini critique
- Human judgment as final arbiter

**Concerns**:
- "Plan compliance" stifles creative refactoring
- Plan should be starting point, not destination
- Over-emphasis on original plan vs. discovered improvements

### 5. **On Documentation Phase**

**Fundamental Flaw**:
- Separate phase guarantees procrastination
- Documentation as afterthought rather than living artifact

**Better Approach**:
- Incremental documentation within each phase
- Ticket itself as living documentation
- Automatic generation from code and commits

## 🤔 Core Philosophical Tension

### Human's Perspective: "Control and Predictability"
- More planning = less deviation
- More constraints = better behavior
- More phases = more quality gates

### Claude's Perspective: "Guidance and Flexibility"
- Lightweight planning = room for discovery
- Smart guidance = better than rigid rules
- Continuous quality = better than phase gates

## 📊 Alternative Synthesis Proposal

### Progressive Context Building
```yaml
# Each phase builds on previous, but allows evolution
plan:
  initial: "2024-01-01"
  revised: "2024-01-02"  # Plans can change
  reason: "Discovered better approach during RED phase"

red:
  planned_tests: 5
  actual_tests: 7  # OK to exceed if valuable
  justification: "Found important edge case"

green:
  planned_files: ["user.ts", "validator.ts"]
  actual_files: ["user.ts", "validator.ts", "types.ts"]
  new_file_reason: "Shared types improve maintainability"
```

### Feedback Over Constraints
- Don't restrict file creation, require explanation
- Don't limit test cases, ensure each adds value
- Don't enforce plan compliance, track deviations with reasons

### Living Documentation
- Ticket evolves through phases
- Each phase documents its decisions
- Final state includes full journey
